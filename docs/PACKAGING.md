# One stack, two packagings

The services in this repository are the only source. There are two ways to run
them, and neither is a fork of the other.

| | ephemeral | persistent |
|---|---|---|
| what | Symbia Imagine | containers |
| built by | `npm run package:imagine` | `docker-compose up` |
| store | pg-mem, dies with the process | Postgres, on a volume |
| origin | one loopback port, `/svc/<id>` | one port per service, 5001-5010 |
| identity | ephemeral key per spawn | configured |
| for | a client sketching, throwing it away | a deployment keeping records |

Both address services **by id, never by port** — the rule from `CLAUDE.md` — so
the same MCP server reaches either without knowing which it is talking to.

## The one MCP server

`symbia-mcp-server` switches on one variable:

```
SYMBIA_BASE_URL=http://127.0.0.1:7717   ->  http://127.0.0.1:7717/svc/catalog/api/…
unset                                   ->  http://localhost:5003/api/…
```

Set, it speaks the one-origin form the imagine host serves. Unset, it uses one
port per service, which is what the containers publish.

I wrote the opposite here first, from reading the compose file's port mapping:
that `service-admin` on 9000 served `/svc/<id>` too. Measured, 9000 returns
HTML — it is an admin UI, not a gateway, and `/svc/catalog/health` is a 404.
Publishing the per-service ports needs the dev overlay:

```
docker-compose -f docker-compose.yml -f docker-compose.dev.yml up -d
```

A one-origin gateway for the persistent packaging does not exist. Worth
building, and not built.

Nothing else in the server knows which packaging it reached, and the operating
mode comes from the host's own response rather than from a flag — a transport
that hardcoded "imagine" would keep saying so while attached to something else.

## What is source and what is generated

Committed:

```
<service>/server/src/     TypeScript — the stack
docker/, */Dockerfile     persistent packaging
imagine/*.mjs             the ephemeral host, shim, ledger, estimator
imagine/plugin/           plugin manifest, mcp config, README, skills
scripts/package-imagine.sh
```

Generated, and gitignored:

```
*/.standalone-routes.mjs  esbuild output per service
imagine/services/         those bundles, plus catalog seed data
imagine/vendor/           workspace libraries, copied for a machine with no workspace
build/plugin/             the assembled plugin tree
build/*.plugin            the archive
```

The distinction is not bookkeeping. `plugin/` was briefly committed with 58
files, and a stale `vendor/@symbia` directory survived a rename inside it
because nothing ever rebuilt that tree from scratch. A committed artifact is a
snapshot of code the directory does not contain, which is the confusion the
build marker in the handshake exists to surface at runtime.

## Building the ephemeral packaging

```
npm run package:imagine     ->  build/symbia-imagine-<version>.plugin
```

Six steps: bundle the services from TypeScript, vendor the workspace libraries,
check that every import has a declared package, assemble, prune, package.

It **refuses** rather than ships when a path contains a character a plugin
installer rejects, or when a key or session file is in the tree. Both were
learned by shipping them — an archive with `@` in 281 paths was refused on
install, and a service signing key generated by a test boot went into the first
archive built.

`check-deps.mjs` is the third step for a reason. Three hand-rolled regexes over
the bundles reported something false in one day: one read a template literal as
a package name, one matched a quote inside an escaped JSON string, and one
looked only at `from "x"` and so never saw `await import("cookie-parser")`
inside a function body. That last one shipped, and identity could not mount.

## Building the persistent packaging

```
docker build -t symbia-base -f docker/Dockerfile.base .
docker-compose up -d
```

Every service image extends `symbia-base`, which carries the built workspace
libraries. Building it first is not optional; without it the service builds
fail with `pull access denied for symbia-base`.

`db-bootstrap` creates one database per service — `catalog`, `identity`,
`runtime` and so on, not one shared schema. A migration has to be applied to
the service's own database; run against the default it fails with
`relation "resources" does not exist`, which reads like a missing table rather
than the wrong database.

`.dockerignore` is load-bearing. It did not cover `imagine/` or `build/`, so
the build context reached 672 MB — shipping the ephemeral packaging's
`node_modules` and vendored libraries to the daemon for images that have no use
for them. Excluding them brought it to 14.6 MB.

## The plugin, and what it will carry

`imagine/plugin/` holds the marketplace plugin's own source: the manifest, the
MCP server entry, the README, and three skills. The packaging script assembles
it with the sidecar and the bundles.

The installer function belongs here too, and is not built: a plugin that can
stand up the ephemeral stack on first use, which today is `shim.mjs` running
`npm install` in its own root and reporting on stderr.
