# Can the manifest classify a component for a deterministic substrate? — results

*14 August 2026. Measured with `scripts/verify-bus-eligibility.mjs` against the
running stack. Predictions were registered in `docs/proposals/canonical-bus.md`
§10 at commit `dd97113`, before the script existed.*

## Answer

**P1 is BROKEN: 11/16.** Five components declare lanes consistent with being
pure and are not. The manifest cannot classify a component for a deterministic
substrate.

**This is evidence FOR the canonical bus, not against it** — specifically for
the import-set mechanism `docs/proposals/wasm-runtime.md` §4 describes.

## P1 — the five the manifest gets wrong

| component | manifest reads | actually disqualified by |
|---|---|---|
| `symbia.io.log` | eligible | io — writes to the execution trace |
| `symbia.io.delay` | eligible | timing — waits `config.ms` |
| `symbia.source.timer` | eligible | clock — `ts: new Date().toISOString()` |
| `symbia.sink.metric` | eligible | io — writes a point to logging |
| `symbia.sink.log` | eligible | io — writes to the platform log store |

**The root cause is a missing axis, not a set of mistakes.** Lanes describe the
epistemic status of a component's *output*. They say nothing about what the
component *does*. `symbia.sink.metric` declaring `out: inherit` is not lying —
it passes its input through unchanged, so `inherit` is exactly right. It is
simply silent about the write to an external store, because the contract has no
vocabulary for effects.

Lane answers *can this value be recomputed?* Bus eligibility asks *what does this
component consume in order to run?* Two axes; the manifest has one.

This is `wasm-runtime.md` §4 measured from the other side. That section says
**imports predict the provenance lane**. True. The converse — that the lane
predicts the imports — is what a manifest-only classifier needs, and it is false
five times in sixteen. An import set is not a nicety for the bus; it is the only
thing that can carry this.

## The sharpest single result: the timer

```
symbia.source.timer.out — declares CANONICAL
  note: "a tick is generated by the platform from declared config;
         nothing external is asserted"
  graph-executor.ts:102 — payload carries ts: new Date().toISOString()
```

A wall-clock read is the textbook non-recomputable value. Replay the graph and
`ts` differs; the tick is not reproducible from the graph and its inputs by any
definition. The note is *almost* right — nothing external is asserted, and the
platform does generate it — but "generated by the platform" was taken to mean
"recomputable," and a clock is the one thing the platform generates that is not.

This is a **fourth** misdeclared port on top of the three found this morning, and
it is worse than those three: they declare `conditional`, which at least signals
doubt. This declares `canonical` outright.

## P5 — held, weakly

```
lane-probe:        1 boundary node of 8
state-lane-probe:  3 boundary nodes of 10
```

Transition sets are derivable statically and are smaller than the node count, as
predicted. **But this ran against two probe graphs and nothing else** — no
production graph is loaded in this runtime, so `energy` and `order-margin` are
unmeasured. Recording this as a weak hold: the mechanism works, the sample is
not representative.

An earlier version of the script read `.nodes` off `GET /api/graphs`, which
returns *summaries* carrying `nodeCount` and no node array. It found nothing and
printed nothing, which reads identically to "no boundaries found." Fixed to fetch
each graph in detail and to report a missing node array loudly. Blank must never
be inferred as a pass — the script now cannot make that mistake quietly.

## Unrelated finding: the standing evidence could not run — and why

`npx tsx` failed on this machine, taking out **every `.mts` script** including
`verify-assistants.mts` (STATUS §5b: "standing evidence, re-run after every
change") and **the entire `npm run test:security` suite**, whose sub-scripts each
invoke `tsx`.

**Fixed. `NODE_ENV= npm install` — and the diagnosis matters more than the fix.**

### An inference I got wrong, recorded because the correction is the lesson

esbuild's error says: *"the `@esbuild/aix-ppc64` package is present but this
platform needs `@esbuild/darwin-arm64`"*, and volunteers that people get here by
copying `node_modules` between platforms. There is an `.ec2-last-sync` marker in
the repo root. I wrote that down as a cross-platform node_modules copy.

**That was wrong.** Checking instead of concluding:

```
$ ls -la node_modules/@esbuild/darwin-arm64/     → total 0
$ ls -la node_modules/@esbuild/aix-ppc64/        → total 0
$ node -p "process.env.NODE_ENV"                 → production
```

All 26 platform directories exist and **all of them are empty**. No binary was
installed for *any* platform. esbuild's resolver found nothing usable, fell
through to the first entry, and reported the mismatch it happened to see — so the
error names a real symptom and the wrong cause, and I repeated it.

The actual cause is **STATUS §6 item 8, recurring**: *"npm run from app-spawned
shells inherits `NODE_ENV=production` and silently omits devDependencies."* The
shell this ran in had `NODE_ENV=production` set. The documented remedy —
*"if npm ever says 'up to date' while node_modules is visibly missing packages,
check `NODE_ENV` first"* — is exactly right and I did not apply it until the
directory listing forced the issue.

Two things worth keeping from this:

- **A tool's own error message is an observation, not a diagnosis.** esbuild
  reported what it could see from inside its resolver. It could not see that
  nothing had been installed at all.
- The lesson in item 8 should be widened, because the symptom this time was not
  "npm says up to date". It was a native binary failing to load. **Before
  reading any native-module error as a code or platform defect, check whether
  the package directory contains anything.**

matching every other script in the file.

## What follows

1. **`symbia.source.timer.out` should not declare `canonical`.** The cheapest
   honest fix is to stop putting `ts` in the payload — the tick counter alone
   *is* recomputable — and let a graph that wants a timestamp ask for one
   explicitly from something that declares itself apocryphal.
2. **Effects need a declaration.** Whether it arrives as a WIT import set or a
   simpler `consumes: []` field on the manifest, the contract needs the second
   axis. The bus cannot be built on lanes alone; that is now measured rather
   than argued.
3. `verify-bus-eligibility.mjs` is standing evidence and should be re-run when
   components change. Its `SOURCE_TRUTH` table is hand-maintained by design —
   when it disagrees with a manifest, the interesting question is which one is
   wrong.
