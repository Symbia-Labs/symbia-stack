# Symbia Energy

A data-center energy monitoring app built **through the Symbia platform API alone**. It is a forcing function: if a piece of it cannot be built through the API, that is a platform defect to be logged — not a reason to reach outside. The running record of those defects is [`API-MEASUREMENTS.md`](./API-MEASUREMENTS.md), which is the primary deliverable of this exercise.

> The rule (Brian, 5 Aug 2026): *If I cannot build a piece of this through the Symbia API alone, that is a platform defect to be logged, not a reason to reach outside.*

## What it does

It models a data center (`dc1`: 4 pods × 40 racks, ~9.6 MW IT design load), streams meter readings, and derives operational metrics — most importantly **PUE** (Power Usage Effectiveness = facility power ÷ IT power) — persisting them as Symbia metrics. The point of the design is **honesty about provenance**: a derived number is only emitted when its inputs are actually present and fresh. There is no path from missing/stale data to a plausible-looking value.

## Architecture

The pipeline is deliberately split at the platform boundary:

```
  energy/sim  ─▶  feeder/pipeline  ─▶  Runtime graph  ─▶  Logging metrics
 (external site)   (device twin,      (validate → join →   (persisted series:
                    delivery only)     derive PUE → sink)    facility_kw, it_kw, pue)
```

- **Outside the platform (legitimately):** the **simulator** in `sim/`. A real data center is not a Symbia component, so its twin shouldn't be one either. It publishes readings exactly as a field site would — there is deliberately **no demo path**, because a special demo path is how demos start lying.
- **Inside the platform:** validation, state/join, derivation, and persistence all run as a **Runtime graph** made of registered components. The external process only *delivers* readings; it holds no state and computes nothing.

### The graph (`graphs/energy-pipeline.graph.json`)

Raw readings hit the ingress (`POST /api/ingress/energy-pipeline`) and flow through:

1. `entry` — `symbia.io.passthrough` (ingress)
2. `valid` — `symbia.logic.filter` (drop readings with no `value`)
3. `join` — `symbia.state.join` (latest facility point `dc1.elec.utility.main.kw` + IT point `dc1.it.main.kw`)
4. `m_facility` / `m_it` — `symbia.sink.metric` (persist `energy.v2.facility_kw`, `energy.v2.it_kw`)
5. `pue` — `symbia.compute.arithmetic` (`{facility_kw} / {it_kw}`)
6. `m_pue` — `symbia.sink.metric` (`energy.v2.pue`)
7. error lane — `pue.error` → `symbia.sink.log` (warn) → collect

Two other graphs are included: `energy-ingest.graph.json` and `energy-pue.graph.json` (the ingest and PUE stages in isolation, useful for testing each hop).

## The one rule that matters: refusal semantics

Every derivation has a **refusal return**. `rollup` emits `incomplete`; `ratio` emits `undefined`. Neither ever returns a number built from bad inputs. In graph terms: only the emitted port fires, and there is **no edge from `incomplete` to a value**. Freshness is a first-class fact — `quality.stamp` ages every reading, so a value that stopped changing hours ago is marked `stale` rather than trusted. The reference implementations live in `service/derive.py` so the semantics are testable without a container rebuild.

## Layout

| Path | What it is |
|---|---|
| `sim/` | Site simulator — `electrical.py`, `workload.py`, `faults.py`, `site_sim.py`. Publishes readings and keeps a **truth ledger** (what was true vs. what was published). |
| `model/site.json` | The 227-point data model for `dc1` (generated by `build_site.py`). Each point has unit, rating, `max_age_s`, balance group, source topic. |
| `graphs/` | Runtime graph definitions (`energy-pipeline`, `energy-ingest`, `energy-pue`). |
| `app/feeder.py` | Device-twin delivery loop — generates readings and POSTs them to the graph ingress. |
| `app/pipeline.py` | Platform-honest driver — loads the graph, executes it, injects readings via `POST /api/executions/{id}/inject`, persists via logging. |
| `service/` | `derive.py` (derivation primitives + refusal semantics), `sinks.py`, `server.py`. |
| `scenarios/` | Fault scenarios as a regression suite (see below). |
| `schema/` | `reading.schema.json`, `point.schema.json`. |
| `data/` | Captured reading streams (e.g. `readings-2026-08-05.jsonl`). |

**Why does `pipeline.py` load and execute the graph itself?** It shouldn't have to — and won't. Executing a graph is meant to be barebones: deliver a reading to the ingress and let the platform run the already-registered graph, with the engine owning hydration, lifecycle, and dispatch. `pipeline.py` performs the extra `POST /api/graphs` (load) and `/execute` (start) steps today only because the runtime doesn't yet hydrate graphs from the catalog on boot, so *something* has to stand the execution up first — `feeder.py` makes the same concession in `ensure_pipeline()`: it probes the ingress and loads/executes the graph only if nothing is already running. That orchestration is scaffolding, not the design. Once the runtime hydrates registered graphs on boot (the catalog is the source of truth; the engine is the handler), those two calls drop away and delivery collapses to a single POST to the ingress — the "driver" goes back to just injecting readings and reading outputs back.

## Scenarios (the regression suite)

Each scenario asserts on the **gap between truth and reported**, which is what makes this a test rig rather than a data faucet:

| Scenario | Exercises |
|---|---|
| `nominal.yaml` | Baseline/control — PUE must be computable every tick; a refusal here is a false positive. |
| `meter-death.yaml` | A meter stops reporting entirely. |
| `meter-freeze.yaml` | A meter reports a frozen (stale-but-plausible) value — caught by freshness ageing. |
| `meter-drift.yaml` | A meter drifts off true. |
| `pod-partition.yaml` | A pod is partitioned from the collector. |

Run the simulator standalone (no broker) to see truth-vs-reported directly — this is how scenarios double as regression tests:

```bash
cd energy/sim
python3 site_sim.py --scenario ../scenarios/nominal.yaml --stdout
python3 site_sim.py --scenario ../scenarios/meter-death.yaml --speed 60 --stdout
```

Drive the platform-honest pipeline end to end:

```bash
cd energy/app
python3 pipeline.py --once   # one tick, prints verification detail
python3 pipeline.py          # run forever (2s ticks)
```

## Status & boundary (as of 5 Aug 2026)

`API-MEASUREMENTS.md` records that, on 5 Aug, an entire energy app was stood up inside Symbia with zero registration, zero gates, and zero ledger entries — which is itself the headline defect: *a property claimed with no mechanism to enforce it*. The measured platform gaps:

- **D1** — no component registration API (`POST /api/components` → 404); the runtime's components are compiled into the bundle.
- **D2 / D2b** — catalog has no `point` resource type, and writes are refused (403) even with logins disabled.
- **D3** — `POST /api/graphs` reachable but rejected a minimal payload (unconfirmed until tried with a valid `GraphDefinition`).
- **D4** — no route to declare an external ingress (`POST /api/integrations` → "Cannot POST").
- **D5** — whether the proxy route table can be derived from a registry (unresolved).

Pieces currently living outside the API (to be re-registered once D1–D4 are addressed) are listed in `API-MEASUREMENTS.md`. The **simulator** legitimately stays outside — it models an external site, which is on the correct side of the boundary.

The graph-based `energy-pipeline` here is the platform-honest target: as the runtime gains graph hydration from the catalog and the registration gates land, the pipeline moves fully inside, and the external footprint shrinks to just the device twin.
